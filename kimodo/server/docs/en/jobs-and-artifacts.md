# Jobs and Artifacts

The server package represents one generation request as a job. Job state and
generated files are managed by `JobManager` and `JobStorage`.

## Job Lifecycle

`JobStatus` currently has five states:

| Status | Meaning |
| --- | --- |
| `queued` | The job has been submitted and is waiting for the background worker. |
| `running` | The runtime is executing generation. |
| `succeeded` | Generation completed and artifact metadata has been recorded. |
| `failed` | Generation raised an exception; `error` stores the traceback. |
| `canceled` | The job was canceled before it started running. |

`JobManager` uses a single-worker queue by default, which is suitable for
GPU-backed generation. `cancel()` can only cancel a future that has not started;
a job already in `running` state is not forcibly interrupted.

## JobRecord

`JobRecord` is the persisted job status record. Its main fields are:

| Field | Meaning |
| --- | --- |
| `job_id` | Unique job identifier generated by `JobStorage.create_job_id()`. |
| `status` | Current job status. |
| `job_dir` | Server-side job directory. Clients should not depend on this path. |
| `progress` | Current progress. At this stage it is mainly `0.0` or `1.0`. |
| `message` | Short status message. |
| `artifacts` | Artifact metadata for generated outputs. |
| `error` | Traceback on failure, otherwise `None`. |

## Storage Directory

The default storage root comes from `KIMODO_JOB_ROOT`. If it is not set, the
server uses `~/.cache/kimodo/jobs`. You can also pass an explicit root through
`create_app(storage_root=...)` or `JobStorage(root=...)`.

A job directory looks roughly like this:

```text
{storage_root}/
  {job_id}/
    request.json
    status.json
    artifacts/
      motion.npz
      motion.bvh
      artifacts.zip
```

`request.json` stores the submitted `GenerationRequest`, and `status.json`
stores the latest `JobRecord`.

## ArtifactRecord

`ArtifactRecord` describes a downloadable file:

| Field | Meaning |
| --- | --- |
| `key` | Artifact key, for example `npz`, `bvh`, `zip`, or `npz_00`. |
| `filename` | File name under the job's `artifacts/` directory. |
| `content_type` | Content type that can be used when serving the download. |
| `size_bytes` | File size. |
| `download_url` | Download path exposed by a future HTTP adapter. |

Generation results do not expose arbitrary local paths to clients. Downloads
should be resolved server-side from `job_id` and `artifact_key`.

## Download Model

The FastAPI adapter exposes:

```text
GET /jobs/{job_id}/artifacts/{artifact_key}
```

The implementation should call:

```python
path, artifact = storage.resolve_artifact(job_id, artifact_key)
```

`resolve_artifact()` reads artifact metadata from `status.json` and ensures the
file is located under the current job's `artifacts/` directory, preventing
clients from using path parameters to download arbitrary local files.

Job status responses intentionally omit `job_dir`, because it is a server-local
path. Failed jobs may include `error` traceback text in this internal API.
